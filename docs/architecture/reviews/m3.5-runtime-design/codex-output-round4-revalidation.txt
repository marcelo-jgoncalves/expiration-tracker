## Decisão central: outbox durável entre claim e publicação

`TransactWrite(SCHEDULED→CLAIMED)` seguido de `SendMessage` direto no handler do producer **não é atômico** — se a Lambda cai entre os dois passos, a ocorrência fica `CLAIMED` sem mensagem em fila, e isso NÃO é coberto pela janela de lookback do próprio producer (que consulta `M` outra chave a cada tick) nem necessariamente pela reconciliação diária a tempo. Fila+DLQ sozinhas não fecham essa lacuna (achado que nenhuma das duas propostas independentes tinha isoladamente — só apareceu na crítica cruzada).

**Decisão**: o claim grava, na MESMA `TransactWriteItems`, um `OutboxEvent` (reusando `shared/outbox/outbox.ts` — nenhum mecanismo de outbox paralelo), `eventType: "ReminderDispatchRequested"`, com um atributo novo e obrigatório **`destination: "SQS_REMINDER_DISPATCH_V1"`** — o único discriminador de roteamento. `OutboxPublisher` (M2/M3, genérico → EventBridge) só processa itens SEM `destination` ou com `destination` que ele reconhece como "EventBridge padrão"; ao encontrar `destination: "SQS_REMINDER_DISPATCH_V1"` ele **ignora explicitamente** o item (não é "o padrão dele, só que falhando" — é um `if` textual no seu filtro de query/processamento). Só o `DispatchOutboxRelay` Lambda processa itens com esse `destination`. Isso é testado diretamente: um item com `destination: "SQS_REMINDER_DISPATCH_V1"` nunca aparece publicado no EventBridge, e um item sem `destination` nunca é consumido pelo relay SQS.

`DispatchOutboxRelay`: gatilho DynamoDB Streams (`NEW_IMAGE`, filtro no event source mapping por `destination`), `reportBatchItemFailures` (partial batch failure do próprio Stream). Para cada registro: (1) lease condicional — `UpdateItem` com `ConditionExpression: attribute_not_exists(leaseOwner) OR leaseExpiresAt < :now`, evita dois relays concorrentes publicando o mesmo item em paralelo; (2) `SendMessage` para `ReminderDispatchQueue`; (3) `UpdateItem` transição `PENDING→PUBLISHED` só após `SendMessage` confirmado. Falha entre (2) e (3) é aceitável — duplicata é absorvida pela idempotência do dispatch (M3, claim por `occurrenceId` determinístico) — falha antes de (2) deixa o item `PENDING`, recuperável.

**Sweeper** (`OutboxSweeperReminderDispatch`, reusa o mecanismo de sweeper já previsto para `OutboxPublisher` genérico, mesmo padrão): EventBridge Scheduler a cada 5 minutos, varre `GSI6PK=RECON#OUTBOX#PENDING` filtrando `destination: "SQS_REMINDER_DISPATCH_V1"` e `occurredAt` mais antigo que um limiar (2 min — cobre falha do Stream/relay, não falha transitória normal), reenvia via o mesmo caminho do relay (lease condicional inclusive). Retry/backoff: nenhum backoff próprio — cada execução do sweeper é uma tentativa; itens que falham repetidamente continuam `PENDING` e acumulam idade, visível em alarme de "outbox pendente há mais de N execuções do sweeper" (reusa o alarme de outbox já documentado em `implementation-blueprint.md`).

## Reconciliação: precisa de fonte real de candidatos, entra no escopo

`runReconciliation` (M3) recebe candidatos como parâmetro injetado — rodar a Lambda via EventBridge sem uma query real produzindo esses candidatos seria false-green (exatamente o P1 #3 do red team). **Decisão**: novo port estreito, implementado contra **GSI6 consultável de verdade** (`data-model.md` §"GSI6 — retenção/reconciliação": `PK=TENANT#t#WORKSTATE#<status>`, `SK=<expiresAt>#<type>#<id>`, já reservado para "jobs pendentes" — reconciliação de Reminder é um uso adicional desse índice já normativo, não um GSI novo):

```ts
interface ReminderReconciliationCandidateSource {
  /** GSI6PK=TENANT#t#WORKSTATE#CLAIMED, GSI6SK=<claimExpiresAt>#OCCURRENCE#<occurrenceId> — projeção: PK, SK, tenantId, occurrenceId, claimExpiresAt, version. Filtro: claimExpiresAt < now. Paginação: LastEvaluatedKey, página lógica máx. 200. */
  listExpiredClaims(input: { tenantId?: string; before: string; pageSize?: number; cursor?: string }): Promise<{ items: ExpiredClaimCandidate[]; cursor?: string }>;
  /** GSI6PK=TENANT#t#WORKSTATE#DST_PENDING, GSI6SK=<windowStart>#POLICY#<policyId> — projeção: PK, SK, tenantId, policyId, timeZone, windowStart, windowEnd. Filtro: windowStart dentro da janela de 7 dias já usada por M3. Paginação: idêntica. */
  listDstCandidates(input: { tenantId?: string; window: { start: string; end: string }; pageSize?: number; cursor?: string }): Promise<{ items: DstReconciliationCandidate[]; cursor?: string }>;
}
```

Namespace `WORKSTATE#CLAIMED`/`WORKSTATE#DST_PENDING` não colide com `RECON#OUTBOX#PENDING` (usado pelo outbox, ver seção anterior) nem com `WORKSTATE#<status>` de outros domínios (Document/Upload, M5+) porque o `PK` inclui `TENANT#t#` — só o outbox usa a chave global sem tenant, todos os outros usos de GSI6 são tenant-scoped por desenho de `data-model.md` §3. Port separado de `ReminderStore` (mesmo princípio de isolamento que levou a `ReminderProducerStore` a ser separado — não dar a rotas tenant-facing acesso a uma query que elas não precisam). Isso muda o escopo original: o "wiring real do GSI6" (item 4 da lista de pendências pós-M3) deixa de ser follow-up separado e entra neste milestone — sem ele, a EventBridge Rule/Scheduler de reconciliação (item 4 do escopo de G8) dispara sobre nada.

Cadência: reconciliação de **claims expirados** roda em minutos (curta — recupera leases/claims excepcionais), separada da reconciliação **DST/materialização diária** (mesmo handler, campo `mode` no evento, concurrency reservada 1 preservada); são responsabilidades complementares ao sweeper do outbox (que recupera publicação pendente), não redundantes.

## Casos obrigatórios de fault injection

OCC concorrente (só um writer vence), claim+outbox atômicos, falha do relay preserva registro para retry (sweeper), duas entregas SQS criam um único `NotificationIntent`, falha de item não repete itens bem-sucedidos do batch, poison message chega à DLQ após 5 receives, claim expirado é recuperado pela reconciliação curta, renew/cancel concorrente faz dispatch cancelar por versão obsoleta, GSI3 encontrado por múltiplos tenants sem misturar contexto, role tenant-facing recebe `AccessDenied` em GSI3/GSI6.

## O que este milestone explicitamente NÃO fecha

Registrar para não ser mal interpretado como "G8 fechado = todos os 5 P1 resolvidos":

docs/architecture/data-model.md-45-## 3. GSIs (todos com chave iniciando por `TENANT#tenantId`, exceto GSI3 — ver exceção documentada abaixo)
docs/architecture/data-model.md-46-- **GSI1 — vencimentos/dashboard**: `PK=TENANT#t#ITEMSTATUS#<status>`, `SK=DUE#<dueDate>#ITEM#i`. Lista próximos/vencidos/arquivados.
docs/architecture/data-model.md-47-- **GSI2 — responsável/categoria**: `PK=TENANT#t#ASSIGNEE#u` ou `TENANT#t#CATEGORY#c`, `SK=DUE#<dueDate>#ITEM#i`. Índices separados se ambos forem padrões frequentes de acesso.
docs/architecture/data-model.md-48-- **GSI3 — scheduler**: `PK=GSI3PK=DUE#yyyyMMddHHmm#NN`, `SK=GSI3SK=TENANT#t#OCCURRENCE#<occurrenceId>`. 4 shards/minuto inicial (decisão Fase 3 Rodada 4); produtor condiciona por status/versão. **Correção Type 1 (ratificada em `implementation-blueprint.md` §9.2/§9.3, decisions-log.md D-028)**: a chave original acima (`PK=TENANT#t#DUE#...`) não é consultável pelo `ReminderProducer` — `Query` do DynamoDB exige PK exata, e o producer do minuto `M` não sabe a priori quais tenants têm ocorrência em `M`. GSI3 é portanto a **única exceção** à regra "toda chave começa com `TENANT#tenantId`": a PK é global (sem `tenantId`), com `tenantId` preservado na SK e no item base para reconstrução segura do contexto. Salvaguardas obrigatórias (detalhadas em `implementation-blueprint.md` §9.2): IAM do índice restrito exclusivamente ao `ReminderProducer` (nenhuma rota tenant-facing tem `Query` neste GSI); projeção mínima, sem conteúdo de negócio sensível; teste de isolamento automatizado provando que nenhuma API tenant-facing o alcança, direta ou indiretamente; dimensionamento de shards por pico global, não por tenant.
docs/architecture/data-model.md-49-- **GSI4 — membership por usuário**: `PK=TENANT#t#USER#u`, `SK=ORG#o#MEMBERSHIP#m`.
docs/architecture/data-model.md-50-- **GSI5 — provider callback**: `PK=TENANT#t#PROVIDER#p`, `SK=MSG#<providerMessageId>`. Localiza a tentativa correta a partir de webhook de delivery/bounce.
docs/architecture/data-model.md:51:- **GSI6 — retenção/reconciliação**: `PK=TENANT#t#PURGE#yyyyMM` ou `...#WORKSTATE#<status>`, `SK=<purgeAfter/expiresAt>#<type>#<id>`. Suporta purge, upload slots vencidos, inbox/outbox e jobs pendentes num índice único. TTL é limpeza auxiliar, nunca gatilho operacional (evita depender de timing assíncrono do TTL para correção — mesma lição do reconciliador de upload da Fase 3 Rodada 6).
