CONTEXT: W3-07 is an unresolved architectural problem: how to fence a tenant undergoing deletion (LGPD/DSR) against resurrection of data, without breaking existing recovery/idempotency mechanisms (Step Functions StartExecution idempotent-by-name, Textract ClientRequestToken, SQS redelivery). Three prior design rounds in docs/architecture/reviews/w3-07-tenant-fence-round2-design/ (read claude-proposal-round1/2/3.md and codex-round1/2/3-critique-full.txt) converged on needing a universal "claim + outcome" protocol per external effect, and paused at 4.8/10 because it was getting very complex (effect-specific state machines for Textract/Bedrock/Step Functions/S3, on top of OCC/TransactWriteItems).

A NEW external analysis (file: expiration-tracker-w3-07-architectural-analysis-2026-08-28.md, repo root) proposes abandoning the universal claim+outcome protocol in favor of a simpler model:
- ACTIVE -> DELETING is the single linearization point / admission fence (transactional, using existing OCC/TransactWriteItems primitives).
- After DELETING: deny all new business mutations and new external effects; in-flight work is NOT guaranteed to complete (liveness for business work is abandoned post-DELETING); late outcomes/callbacks are discarded as no-ops, never persisted as new business state.
- A quiescence barrier (bounded wait + active verification) confirms no further tenant-owned writes are possible.
- A durable, checkpointed purge (Step Functions-based) handles DynamoDB (main table + bff-session-table + other tenant-owned tables) and S3 (versioned buckets, ListObjectVersions, delete markers, pagination, DeleteObjects.Errors[], retries) with a physical-deletion proof step.
- S3 OCR artifact keys should become deterministic/tenant-scoped instead of `ocr/<runId>/<randomUUID>.json` (also flags this as an independent idempotency bug: PutObject success + SendTaskSuccess timeout can produce two physical OCR artifacts under different random UUIDs today).
- Bedrock has no ClientRequestToken-equivalent idempotency key; the analysis says the fence doesn't need to solve this because after DELETING no new Bedrock calls are made anyway, and pre-DELETING Bedrock semantics are unchanged (today's actual behavior, whatever it is, is not itself part of W3-07's scope).
- TenantMutationExecutor / structural boundary requiring TenantLifecycleRecord.status=ACTIVE in the SAME transaction as any business mutation, enforced structurally (repository/transaction-builder layer), with ESLint as a secondary guardrail only.
- Atomic bootstrap of IdentityMapping+TenantLifecycleRecord(ACTIVE)+User, refusing reprovisioning if lifecycle is DELETING/DELETED.
