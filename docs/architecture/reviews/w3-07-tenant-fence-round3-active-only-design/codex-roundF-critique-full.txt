## A — S3 presigned uploads: PARTIALLY CLOSED

The central argument is sound:

- A quarantine object alone is physical tenant data, not resurrected application state.
- Presigned upload TTL is concretely bounded at 900 seconds.
- Tenant-visible promotion must be fenced at an atomic DynamoDB admission point.
- Residual quarantine objects belong to physical purge.

But “the finalizer transaction gets the fence” is too coarse.

The upload and malware workers first persist `uploadEvidence`, `malwareEvidence`, and `SCANNING` into the existing `Document` or `DocumentSubmission`.

Those are tenant business mutations themselves and must each carry the `ACTIVE` condition—not merely the final `CLEAN` transition.

There is no separate idempotency/dedup row in these four workers.

Dedup state is embedded in the tenant records, such as `malwareEvidence.scanResultId`.

Therefore it does not create a hidden resurrection category, but it confirms that every evidence transaction belongs to `TenantBusinessMutation`.

More importantly, both promotion functions perform the S3 copy before the fenced DynamoDB transaction:

- [advance-after-evidence.ts](/C:/Users/Usuario/Desktop/projects/expiration-tracker/src/modules/document/application/advance-after-evidence.ts:111)
- [advance-after-submission-evidence.ts](/C:/Users/Usuario/Desktop/projects/expiration-tracker/src/modules/subject/application/advance-after-submission-evidence.ts:66)

The sequence is:

1. Copy quarantine → clean.
2. Verify the clean object.
3. Commit `status=CLEAN` and `cleanObject`.

If `ACTIVE→DELETING` wins between steps 1 and 3, the transaction correctly fails, but a new clean-bucket object has already appeared.

That is not logical resurrection if every downstream writer is fenced.

It is nevertheless sensitive physical residue and may emit an extraction event.

The design must consequently require:

- Purge discovery of clean objects independently of a surviving `Document` row.
- Fencing of the extraction-run creation triggered by that orphan copy.
- Either compensating deletion after a failed promotion transaction or explicit purge/reconciliation coverage.

The 900-second TTL finding closes presign issuance duration, but not overall quiescence.

The repository’s worker queues retain messages for 14 days, with DLQs retaining them for 4 days.

Lambda timeout bounds one invocation; it does not bound:

- SQS redelivery.
- EventBridge/S3 delivery retries.
- DLQ replay.
- Scheduled reconciliation.
- Existing notification leases.
- A message waiting before its next invocation.

Thus `max(900s, 60s, 600s) + 900s = 1800s` is not yet a valid system-wide quiescence bound.

It can become valid only if deletion explicitly disables/drains or permanently fences all delayed work, making quiescence unnecessary for non-resurrection.

That is the preferred interpretation: the fence provides safety indefinitely; time bounds only operational cleanup.
