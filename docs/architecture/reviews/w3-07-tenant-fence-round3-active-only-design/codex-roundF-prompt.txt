CLOSURE PROPOSALS FOR THE 3 NAMED GAPS PLUS 2 MORE:

(A) S3 presigned uploads - NOT "generic residual risk" anymore, concrete policy:
1. Quiescence bound now has a real number: max(all presign TTLs = 900s, all Lambda/consumer timeouts = 60s, ASL waitForTaskToken TimeoutSeconds = 600s) + a fixed safety margin (proposing 15 minutes flat, i.e., bound = 900s + margin, since 900s already dominates) - this is the first concrete, non-hand-waved number produced in this review.
2. Non-resurrection does NOT depend on preventing a late upload into the quarantine bucket (a raw byte blob in quarantine, with no business meaning, is not itself "tenant business state" - it is inert until promoted). The actual gate belongs on the PROMOTION step: the finalizer workers (upload-finalizer, submission-finalizer, malware-result, submission-malware-result) already perform a transactWrite that creates/updates the real Document/DocumentSubmission row - this is exactly a `TenantBusinessMutation` under the typed-lane model from Round E, so it already gets the ACTIVE ConditionCheck for free once that lane is implemented. A late upload via a still-valid presigned URL can create quarantine bytes, but those bytes can never become a Document/business record after DELETING, because the finalizer's fenced transaction will fail. The quarantine bytes themselves are physical residue covered by the existing S3 purge phase (quarantine bucket is already in the inventoried bucket list).
3. Therefore S3 presign is closed as: "bounded by TTL (real number: 900s+margin) for when new *quarantine* writes can still land, non-resurrection guaranteed by fencing the PROMOTION step (already required by the typed-lane model), and purge covers residual quarantine bytes regardless of promotion outcome."

(B) SES - explicit product/legal question, engineering recommendation conditioned on the answer (not invented):
Apply the same mechanical fix as quota.consume(): convert email-delivery-workflow.ts's SUBMITTING claim from a single-item buildVersionedUpdate to a 2-item TransactWriteItems (the same Update + a ConditionCheck on TenantLifecycleRecord ACTIVE), requiring a NotificationStore port extension (same class of change as IdentityStore's). This closes ENGINEERING admission the same way as Textract/Bedrock/Step Functions - a send only proceeds if admitted atomically while ACTIVE.
QUESTION FOR PRODUCT/LEGAL (explicitly not answered by engineering): once a send has been atomically admitted (SUBMITTING claim committed) before DELETING, and the actual SES API call happens after DELETING (a real gap - the SES call is not inside the DynamoDB transaction), is it acceptable for that already-admitted email to still be delivered to the recipient? Two options:
  - Option 1 (recommended by engineering, matches Codex's Round E view): YES, acceptable - "immediate blocking" is interpreted as blocking NEW admissions at the atomic admission point, not interrupting an admitted-but-in-flight provider call. Rationale: SES has no cancel-in-flight API once a call is made; building a lease/drain protocol to prevent this narrow race (admission commits milliseconds before DELETING, SES call happens milliseconds after) would be a large addition (coordinated drain between the lifecycle transition and every in-flight notification worker invocation) for a residual window bounded by the worker's own short execution time (Lambda timeout <=60s per the inventory above) - disproportionate given AGENTS.md's own overengineering guardrail.
  - Option 2: NO, not acceptable - if this is a hard LGPD requirement (not just an operational preference), a lease/drain protocol is required: the lifecycle transition would need to acquire/verify no outstanding SUBMITTING leases before completing, or the transition itself would need to invalidate/await all in-flight SUBMITTING claims (bounded by their own lease TTL, which the design already has - email-delivery-workflow.ts already uses `leaseDurationMs`).
This is registered as a PRODUCT/LEGAL DECISION, not resolved by this review - if Marcelo/legal has not decided, Option 1 is the engineering default recommendation but the document states this explicitly as conditional, not invented as fact.

(C) StartExecution post-DELETING - explicit semantics:
1. New StartExecution (a genuinely new ExtractionRun) is denied once DELETING, by the same transactional-admission fix already proposed for start-extraction-run.ts (convert ExtractionRunStore.putIfAbsent to a 2-item TransactWriteItems with the ACTIVE ConditionCheck).
2. Retry of an EXISTING run: once that fix ships, every ExtractionRun row in the table is guaranteed to have been created under a fenced, ACTIVE-checked transaction - its mere existence (regardless of the tenant's CURRENT lifecycle state at retry time) is durable proof of prior valid admission. Therefore start-extraction-run.ts's existing behavior (call startExecution() unconditionally whenever the row already exists, whether just-created or pre-existing - see the module's own doc comment) remains correct and needs NO new gate on the retry path - only the FIRST creation of the row needs the fence. This resolves the specific "retry wrinkle" flagged in Round E (distinguishing an admitted run being retried from an unadmitted legacy run) - after the fix, there is no such thing as an unfenced ExtractionRun going forward; a currently-running system would need exactly one migration note (any ExtractionRun rows created BEFORE this fix ships lack the guarantee, and should be treated as legacy/audited once, not as an ongoing gap).
