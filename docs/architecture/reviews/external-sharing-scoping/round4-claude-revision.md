# Rodada 4 — Revisão Claude (ExternalShareLink), fechamento

**Autor**: Claude (Rodada 4). **Data**: 2026-09-07. Responde aos 3 achados que impediram o fechamento na Rodada 3 (Codex: pesquisa 8,7/10, design 8,4/10 — os demais achados das rodadas 1-3 o próprio Codex já declarou fechados e não reabertos).

## Fonte primária AWS nova (fecha a lacuna de pesquisa apontada na Rodada 3 para o Critério 4)

AWS Prescriptive Guidance / re:Post (consultado 2026-09-07) — https://docs.aws.amazon.com/prescriptive-guidance/latest/presigned-url-best-practices/overview.html e https://repost.aws/knowledge-center/presigned-url-s3-bucket-expiration: **confirma como fato documentado pela AWS, não hipótese interna, que não existe mecanismo de revogação direta de uma URL presigned antes do seu próprio prazo de expiração** — a única forma de invalidar uma URL presigned já emitida é revogar a credencial usada para assiná-la (rotação de chave de longa duração ou invalidação da sessão STS), o que neste projeto significaria invalidar a role IAM da Lambda inteira, claramente desproporcional para revogar 1 link. Isso confirma que a janela residual (Critério 4) não é uma limitação inventada por analogia interna — é uma propriedade documentada do próprio mecanismo AWS que D-215/216/217 já usam, portanto correta como "propriedade sistêmica aceita" e não um gap deste design específico.

## Achado 1 (Rodada 3) — contador atômico não libera slot na expiração natural

**Aceito, corrigido.** Mecanismo de reconciliação preguiçosa e limitada (bounded, cap=5 então custo desprezível): quando `activeExternalShareLinkCount >= 5` na criação, ANTES de rejeitar com 400, o serviço faz uma `Query` sobre os (no máximo 5) links ativos daquele Document (GSI1, mesmo índice da Decisão de listagem) e, para cada um cujo `expiresAt < now()`, executa uma reconciliação: `status: ACTIVE → REVOKED` (motivo `EXPIRED_RECONCILED`, distinto de `revokedByUserId` humano) + decrementa `Document.activeExternalShareLinkCount` — na MESMA transação que tentará a criação em seguida (não duas transações separadas: se a reconciliação libera pelo menos 1 slot, a criação prossegue na mesma chamada; se não libera nenhum, retorna 400 "limite atingido" normalmente). `activeExternalShareLinkCount` usa `if_not_exists(activeExternalShareLinkCount, :zero) + 1`/`- 1` em toda escrita (fecha o achado de backfill/underflow para Documents anteriores ao campo novo — nunca assume que o atributo já existe). Condição de decremento nunca permite ir abaixo de 0 (`ConditionExpression: activeExternalShareLinkCount > :zero` no caminho de decremento). Isso fecha o drift: um documento com 5 links todos expirados naturalmente sempre consegue criar um 6º, porque a PRÓXIMA tentativa de criação sempre reconcilia antes de rejeitar — nunca fica travado esperando um humano revogar manualmente algo que já expirou.

## Achado 2 (Rodada 3) — semântica de revalidação incompleta após transições de domínio (`SUPERSEDED`/`ARCHIVED`)

**Aceito, resolvido explicitamente (não deixado ambíguo).** Decisão: **o link congelado nunca revalida `DocumentVersion.state` nem `Document.status` a cada acesso** — só revalida `DocumentFile.scanStatus = "CLEAN"` E presença de `cleanObject` (disponibilidade física do byte compartilhado). Racional explícito: a Decisão 11 (Rodada 2, "congelar sempre") decidiu deliberadamente que compartilhar é equivalente a "entregar uma cópia" do estado no momento da criação — uma cópia entregue por e-mail não se autodestrói quando o documento original muda de versão ou o Document é arquivado depois; o link se comporta da mesma forma, pelo prazo (≤30 dias) que o admin escolheu. Consequência aceita e nomeada: um `Document` arquivado ou uma `DocumentVersion` que virou `SUPERSEDED` depois da criação do link **continuam servindo o snapshot compartilhado** até o link expirar/ser revogado manualmente — isso NÃO é um "vazamento" no sentido de expor dado além do que já foi deliberadamente compartilhado, é a semântica de "cópia" que a própria Decisão 11 já escolheu. O único caso que efetivamente invalida o acesso é remoção FÍSICA do arquivo (purge LGPD/`document-file-reconciliation`, D-183) — capturado exatamente pela revalidação de `scanStatus`/`cleanObject` já proposta, sem necessidade de checar o resto da árvore de estado do domínio. Isso fecha a ambiguidade apontada: a regra agora é explícita e única, não duas regras conflitantes (congelar E revalidar tudo).

## Achado 3 (Rodada 3) — mitigação de vazamento de token sem fronteira concreta

**Aceito, corrigido com verificação por leitura.** Dois mecanismos concretos, ambos já existentes no projeto (reuso, não invenção):
1. **Log de aplicação**: `schemas/sensitive-fields.json`'s `redactedValuePatterns` já inclui `inlineKeyValueSecret`, regex `(token|password|secret|apikey|api_key|authorization)\s*[:=]\s*[^\s,;]+` — isso casa literalmente contra a query string bruta `?token=<selector>.<secret>` sempre que ela for logada como parte de uma string (ex. `event.rawQueryString`, mensagem de erro, corpo de request logado) porque o padrão é aplicado a QUALQUER valor string em profundidade (`redactValue`/`redactString`, `src/shared/observability/redactor.ts`), não só a chaves nomeadas `token`. **Regra explícita nova**: o handler desta rota (`external-share-handler.ts`, Lambda dedicada, mesmo padrão de isolamento de `document-archive-guest-handler.ts` — `authorization_type = NONE`) nunca loga `event.rawQueryString`/`event.queryStringParameters` DIRETO sem passar pelo `defaultRedactor` — mesma disciplina que qualquer handler já deveria seguir, mas nomeada aqui explicitamente porque é a única rota deste design cujo segredo INTEIRO vive na query string (guest tokens de upload vivem no PATH, não na query — achado real desta verificação: `/document-archive/guest/document-requests/{token}/...`, nunca `?token=`, diferença que eu não tinha notado nas rodadas 1-3). **Correção de desenho**: mudo a rota de `GET /external-share/{shareId}?token=...` para `GET /external-share/{shareId}/{token}` (token no PATH, mesmo padrão do precedente D-143, nunca inventando um transporte novo) — isso também torna a mitigação de log mais forte por padrão (paths tendem a ter tratamento de log mais consistente neste projeto que query strings, confirmado pelo próprio precedente).
2. **Access log da API Gateway**: a rota nova usa o MESMO `default_route_settings`/formato de log já configurado no stage (`infra/modules/api-gateway/main.tf`) — verificado por leitura que o projeto não customiza `access_log_settings` por rota hoje (não há um `$context.path`/query customizado a ajustar). Como o token agora vai no PATH (correção acima), e o formato de access log padrão do projeto já não loga corpo/query de forma bruta (confirmado: sem `access_log_settings` customizado achado em `main.tf`/`api-gateway/main.tf` além do já existente), o caminho onde o segredo poderia vazar por access log de infraestrutura é fechado pela mudança de transporte, não por uma exceção nova de configuração.

## Modelo final ajustado

Rota final: `GET /external-share/{shareId}/{token}` (path-only, token nunca em query string). `Document.activeExternalShareLinkCount?: number` novo (sparse, tratado com `if_not_exists`). Reconciliação de expiração lazy incorporada à Decisão de criação (achado 1). Regra de revalidação de acesso reduzida e explícita (achado 2): só `scanStatus="CLEAN"` + `cleanObject` presente + `TenantLifecycleRecord=ACTIVE` (Rodada 2, achado 15) + `status=ACTIVE` do próprio link + `expiresAt` no futuro — nunca `DocumentVersion.state`/`Document.status`.

## Fechamento

As 3 objeções da Rodada 3 foram tratadas com mecanismo concreto (não promessa de "resolver na implementação"): reconciliação lazy limitada a 5 itens, regra de revalidação única e explícita (nunca ambígua), e transporte corrigido para path (nunca query) com o mecanismo de redaction já existente citado por nome de arquivo/regex real. Nenhum achado das Rodadas 1-3 foi reaberto — o Codex já os declarou fechados na própria Rodada 3 e este documento não os toca de novo.
