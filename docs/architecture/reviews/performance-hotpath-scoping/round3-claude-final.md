## D-D final — `EphemeralTelemetryMutation`, emenda formal ao W3-07

**Contrato da nova lane** (paralela a `executeTenantBusinessMutation()`, nunca a substitui para dado de negócio real):

- **Allowlist fechada de tipos**: só `API_REQUEST` nesta decisão. Qualquer tipo novo que queira essa lane exige nova decisão Type 1, nunca adição silenciosa.
- **Proibição explícita**: nenhum item desta lane pode conter dado de negócio, PII direta, entitlement ou capability — só contador+metadados de janela. Enforcement: revisão de código + comentário `AGENTS.md`-style no writer citando esta decisão, mesma disciplina de `shared-must-not-reach-modules` (dependency-cruiser) já usada para outra invariante estrutural do projeto.
- **Quando a escrita é permitida**: depois de uma leitura *stale* de `ACTIVE` no `RequestContextResolver` (ele já revalida lifecycle a cada request — não é uma leitura nova, é o mesmo resultado que already autoriza a operação de negócio da request). A lane não pula a checagem de lifecycle; ela só não repete o `ConditionCheck` transacional no mesmo `TransactWriteItems` do contador.
- **Chave e janela**: `PK=TENANT#<id>#QUOTA`, `SK=TYPE#API_REQUEST#<floor(epochSeconds / windowSeconds)>` — corrigido para usar `windowSeconds` real (vindo da config existente do `TenantQuotaRecord`), não um valor fixo de 60 inventado por mim.
- **Atributo TTL correto**: `purgeAfterTtl = windowEnd + 30d` — mesmo nome de atributo já usado em `MembershipInviteRateLimitRecord`/`InvitationTokenPointer` (`purgeAfterTtl`), não `ttl` (erro meu, corrigido).
- **Item permanece descobrível pelo purge real**: a chave `TENANT#<id>#...` já cai dentro do padrão que `tenant-purge-scan.ts`'s `ScanCommand`/`PURGE_DELETE` cobrem estruturalmente (mesma cobertura que `MembershipInviteRateLimitRecord` já tem hoje, verificado em `privacy-lgpd.md` §4.2) — a lane não depende só do TTL nativo do DynamoDB (que a AWS documenta como assíncrono/best-effort, sem limite rígido — correção aceita) para desaparecer definitivamente; o scan de purga do W3-07 continua sendo o mecanismo de garantia forte, o TTL é só uma limpeza antecipada best-effort.
- **Leituras ignoram buckets expirados**: `consume()` trata um item com `purgeAfterTtl` no passado como inexistente (recria a janela), nunca como "quota zerada válida" de um bucket morto.
- **Ausência do item nunca concede direito comercial**: esta lane nunca é reusada para `AI_CALL`/`UPLOAD_*`/`IMPORT_*` — esses continuam 100% no mecanismo transacional fenced atual, sem exceção, sem migração futura "para simplificar" sem nova decisão.
- **Teste adversarial obrigatório antes de fechar a implementação** (registrado aqui para constar no DoD/G-V3 de quando isso for implementado, não implementado nesta rodada): simular a corrida `ACTIVE` observado → `DELETING` → escrita da lane efêmera → purge já rodou → confirmar que o resíduo (a) nunca é lido como direito de negócio, (b) é apagado pelo próximo ciclo do sweeper/scan de purga, (c) gera métrica/alarme se sobreviver além do `purgeAfterTtl` esperado — resíduo pós-`DELETED` é um sinal de operação, não silêncio.

## Correções técnicas aceitas (fora do D-D em si)

- **Distinção de falha no `UpdateItem` da quota**: `ConditionalCheckFailedException` → `QuotaExceededError`/429 (comportamento já existente, mantido). Falha de **dependência** (DynamoDB indisponível/throttled, timeout) → fail-open, permite a request e emite métrica/log de degradação. Erro de **validação/corrupção/bug** (ex. item com forma inesperada, exceção não mapeada) → **não** tratado como indisponibilidade — propaga como erro real (5xx), nunca mascarado como "deixa passar por precaução". As três classes de erro são tratadas por branches distintos no código, nunca um `catch` genérico que trata tudo como a mesma coisa.
- **Recalibração do API Gateway**: abandono o critério "acima da soma esperada em dev" (correto, não é durável). Critério revisado: o valor de `rate`/`burst` do throttle coarse deve ser derivado de (a) a capacidade de concorrência real que o BFF/Resource Lambda sustentam sem degradar (função de `reservedConcurrency`/`provisionedConcurrency` configurados), e (b) uma margem explícita acima do agregado esperado de `limite-por-tenant × tenants-ativos-esperados-simultaneamente`, não um número redondo escolhido por conveniência. O valor exato fica para quando isso for implementado (com medição real), não fechado nesta rodada de protocolo — a decisão aqui é o **critério**, não o número.
