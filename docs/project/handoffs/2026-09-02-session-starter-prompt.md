## Padrões operacionais validados nesta sessão (repita-os)

- **Ao herdar uma classificação de risco de uma sessão anterior ("provavelmente nível 3-4"), sempre fazer o scoping real antes de aceitar** — a estimativa otimista do handoff anterior sobre `DocumentFile` (design já existe, "só falta implementar") ignorava que o *mecanismo* de storage/scan nunca existiu para este domínio, só a *semântica*. O scoping real revelou nível 5.
- **Protocolo Claude↔Codex em 4 rodadas curtas funcionou bem para uma decisão de arquitetura real** — cada rodada fechou achados concretos e verificáveis (corrida de PRINCIPAL, contradição de correlação de evidência, uso indevido de GSI6 contra uma decisão já `APPROVED`), nunca "polimento" sem achado novo. Pesquisa externa pontual (formato real de um finding do GuardDuty) fechou uma rodada que teria ficado ambígua só com raciocínio interno.
- **Depois de fechar o design, comece a implementação real na mesma sessão se o orçamento permitir, mas pare numa fronteira coerente e testável** — a fatia entregue (entidade + fence transacional do PRINCIPAL) é um incremento real, 100% testado com G-V3, sem deixar nada "meio implementado": os métodos que não foram feitos (`applyFileScanResult`, reconciliação, presign, rota HTTP) simplesmente não existem ainda, não existem pela metade.
- **Cuidado ao ativar um gate novo numa fatia parcial**: o gate `fileSetSealed` em `commitUpload()` foi desenhado mas propositalmente NÃO ativado — ativá-lo teria quebrado a suíte e o fluxo HTTP e2e existente (nenhuma rota chama `reserveFiles()` ainda). Descoberto rodando a suíte completa antes de declarar a fatia pronta — sempre rodar `npm test` completo (não só o arquivo que você tocou) antes de considerar um gate novo seguro.
- **G-V3 em mecanismos de concorrência exige simular a corrida certa, não qualquer corrida**: a primeira versão do teste "fecha a corrida entre duas chamadas concorrentes" passava mesmo sem o fence, porque duas chamadas com o MESMO `expectedVersion` já colidem pela OCC comum de qualquer Update — isso não prova que o fence extra faz alguma diferença. O teste certo usa um `expectedVersion` FRESCO (pós-primeira reserva) na segunda chamada, isolando exatamente o que o fence adicional (`fileSetSealed`) contribui além da OCC padrão.
- **Um fake de teste pode ter uma lacuna real no parser de condição, não só no código de produção** — `in-memory-store.ts` não suportava `attribute_not_exists(#nome)` dentro de um grupo OR sobre um atributo qualquer (só PK/SK). Sintaxe DynamoDB real e válida; corrigido no fake, não contornado no código de produção.
- **Capture o `databaseId` do run de CI/CD ANTES do push/merge, espere um `databaseId` diferente aparecer, só então faça polling desse run específico** — continua válido, usado nos dois merges desta sessão.
- **Confirme infra nova ao vivo contra `dev`** (`aws lambda get-function-configuration --profile claude-dev`) em vez de assumir que o CD aplicou corretamente só porque o job passou.
