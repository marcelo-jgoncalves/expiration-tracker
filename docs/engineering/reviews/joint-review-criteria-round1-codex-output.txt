# Princípios de Engenharia — Expiration Tracker

> Adaptado do padrão observado no projeto irmão `event-discovery-platform` (mesmo usuário), não copiado literalmente — o primeiro princípio abaixo já recomenda isso: adotar só o que a complexidade real deste projeto justifica.

1. **Sofisticação segue complexidade observada, não medo hipotético.** Não adicionar mecanismo (sharding extra, cache, retry exótico) antes de evidência real de que o caso simples não basta. Exemplo já aplicado: `TenantQuota` usa fixed-window, não sliding-window/leaky-bucket, porque fixed-window já satisfaz "decremento atômico sem race condition" — sliding-window só entraria com evidência de abuso real em produção.

2. **Decisões caras-de-mudar são fechadas cedo; decisões baratas-de-adicionar são adiadas.** Chaves de partição/GSI, contratos de schema, fronteiras de módulo e estratégia de idempotência são Type 1 (protocolo Claude↔Codex, `AGENTS.md` §4). Reserved concurrency, batch size, thresholds de alarme são ajustáveis depois sem migração — não precisam da mesma rigidez de decisão.

3. **Restrições de infraestrutura de terceiros são domínio, não detalhe.** DynamoDB `Query` exige PK exata (é por isso que GSI3/GSI6 têm chave global — não um detalhe de implementação, é a forma como o produto pode ou não escalonar). EventBridge Scheduler não envelopa payload em `detail` como Rules legadas (é por isso que os handlers leem o evento no nível raiz) — restrições assim vão em comentário no código-fonte, não só em doc.

4. **Nenhum caminho crítico do produto pode ficar bloqueado por um componente auxiliar.** Idempotência/outbox/reconciliação existem para que uma falha de fila/rede nunca perca um lembrete silenciosamente — mas o inverso também vale: a materialização de ocorrências não pode ficar bloqueada esperando o outbox confirmar publicação (por isso o outbox é assíncrono via relay, não síncrono no caminho de escrita do agregado).

5. **Honestidade sobre simplificação deliberada.** Toda simplificação consciente (ex.: `EX-001` em `exceptions.md`, judgment calls documentados em `NEXT_SESSION_PROMPT.md`/`session-log.md`) precisa de gatilho de reavaliação explícito — não "revisar depois" vago, mas uma condição concreta ("quando M4 existir", "quando o bug upstream for corrigido").

6. **Auditar contra a realidade, não contra a documentação.** `ARCHITECTURE STATUS`/`ENGINEERING FOUNDATION STATUS` só mudam com evidência operacional real (teste real, CI real, deploy real) — nunca porque um documento foi atualizado para dizer que algo está pronto. A Engineering Maturity Review e as 3 rodadas de revisão da implementação de M3.5 (não só do design) são a aplicação direta disso.

7. **A segunda IA de revisão só vale o que ela consegue provar.** No protocolo Claude↔Codex (`AGENTS.md` §4), uma nota alta sem evidência de arquivo:linha específica, ou sem rodar o comando que prova o achado, não fecha rodada — ver `docs/engineering/change-risk-scale.md` para quando o protocolo é obrigatório.

> Formaliza (padrão adotado do `event-discovery-platform`, ADR-009 de lá) algo que este projeto já fazia informalmente desde M3.5 como "Camada 1/2/3" (`docs/architecture/m3.5-runtime-design.md`). Mapeamento explícito abaixo — não é um sistema novo, é dar nome ao que já existe e fixar a regra de bloqueio de cada tier.

## Tier A — toda PR (`guardrails` no CI, obrigatório, bloqueia merge)

`typecheck`, `lint`, `check-boundaries` (dependency-cruiser, grafo real de imports), `validate-schemas`, testes unit+contract+integration (fakes em memória) + synth de infra CDK, `npm audit --omit=dev` (produção, bloqueante — zero vulnerabilidade não tratada), `npm audit` dev (informacional, cruzar com `exceptions.md`), SBOM CycloneDX. Corresponde à **Camada 1** do plano de testes de milestones com runtime real (ex. M3.5).

**Vermelho aqui bloqueia merge em `main`, sem exceção.**

## Tier B — merge para `develop`/antes de deploy real (`dynamodb-integration` no CI + testes manuais de Camada 2/3)

Testes contra serviços reais via container (DynamoDB Local, LocalStack/Testcontainers) — prova `ConditionExpression`/`TransactWriteItems`/`Query` reais, não a aproximação da fake em memória. Corresponde à **Camada 2**. Não bloqueia `guardrails`, mas bloqueia a decisão de fazer deploy real de um milestone que dependa do componente testado.

## Tier C — antes de declarar um gate de engenharia fechado (G1-G8) ou promover `ARCHITECTURE STATUS`

Sandbox AWS efêmero: IAM real (`AccessDenied` para role sem permissão), redrive de DLQ real, invocação real de EventBridge Scheduler/Rule, teste de restore real (`disaster-recovery.md` §6). Corresponde à **Camada 3**. Gate mais caro (custo real de AWS, tempo de setup) — só roda quando o milestone genuinamente depende dele, nunca "por rotina".

## Regra de bloqueio

- Tier A vermelho: PR não mergeia.
- Tier B vermelho: milestone não é considerado testado contra runtime real, mesmo com Tier A verde — não declarar "implementação pronta" nesse estado (foi o erro que quase aconteceu em M3.5 antes da Camada 2 rodar).
- Tier C vermelho, ou não executado: gate de engenharia (G1-G8) permanece aberto, `ARCHITECTURE STATUS` permanece `NOT APPROVED`, independente de quão verde Tier A/B estejam.

## Regra prática

Ao ficar em dúvida entre dois níveis adjacentes, tratar como o nível mais alto — o custo de uma rodada de debate a mais é sempre menor que o custo de uma decisão Type 1 tomada sem revisão (ver `docs/engineering/principles.md` #2).

Isso não substitui o julgamento listado em `AGENTS.md` §4 ("aplicar bom senso de engenharia") — é uma referência para calibrar esse julgamento de forma consistente entre sessões.

Motivo: o achado do Checkpoint 2-9 (G10 FAIL) é que os boundaries de módulo estavam limpos só por disciplina, sem mecanismo automatizado. Motivo: mudar a configuração do GitHub (branch protection) altera o fluxo de trabalho do usuário (hoje push direto pra `main`) fora do escopo de uma edição de arquivo — tratado como decisão que precisa de confirmação explícita do usuário, não aplicada silenciosamente nesta sessão. ## E-007 — Não injetar `SecureLogger` diretamente na lógica pura dos workers (dispatch/producer/reconciliation); fechar G8 via testes dedicados em vez disso

Motivo: `producer.ts` documenta explicitamente que "this module stays observability-agnostic" — telemetria fica para a camada de handler Lambda real, que ainda não existe (mesmo padrão de M0-M3: lógica pura testável primeiro, wiring de runtime depois). - `test/unit/reminder/producer.test.ts`: prova que uma falha genuína de store (não uma perda de race de OCC) numa claim específica cai em `failed`, sem abortar o resto do tick nem mutar a ocorrência (fica disponível pra retry) — o caminho `failed` do producer nunca tinha sido exercitado por nenhum teste antes (só afirmado vazio no caminho feliz).

G8 permanece **não-PASS pleno** — "observável em execução real" continua exigindo o handler Lambda + fila real de M4+, isso não muda com testes. Mas a parte de "replay/reconciliation testados" da definição do gate agora tem evidência real, o que não existia antes desta sessão.

## E-008 — Boundary transitivo real via `dependency-cruiser`, não só ESLint; achado real de código corrigido no processo

Motivo: o red team formal (Checkpoint 12) apontou que a regra `no-restricted-imports` do ESLint (E-004) só compara o texto literal do specifier do import, não o grafo real — não pega reexport transitivo, `import()` dinâmico, nem (descoberta ao testar de verdade) imports relativos dentro do MESMO módulo, porque a string `"../ports/foo.js"` nunca contém a substring `modules/*/ports` que os padrões glob esperam. Adicionado `dependency-cruiser` (`npm run check-boundaries`, wired no CI) como enforcement AUTORITATIVO — resolve o grafo de módulos de verdade. ESLint mantido só como feedback rápido no editor, comentário do arquivo agora deixa isso explícito.

Ao testar a nova ferramenta contra o código real (não só contra um caso sintético), ela encontrou **2 violações genuínas já existentes**: `src/modules/expiration/domain/expiration-item.ts` e `audit-event.ts` importavam `EntityKey`/`TransactPutEntry` de `../ports/expiration-store.ts` (domain→ports, boundary real) em vez do `shared/dynamodb/occ.ts` já usado corretamente pelo módulo `reminder` para o mesmo tipo — `expiration-store.ts` tinha uma cópia própria e estruturalmente duplicada de `EntityKey`/`TransactPutEntry`/`TransactUpdateEntry`/`TransactWriteEntry`/`isTransactionCanceled`. ## Decisão central: outbox durável entre claim e publicação

`TransactWrite(SCHEDULEDâ†’CLAIMED)` seguido de `SendMessage` direto no handler do producer **não é atômico** â€” se a Lambda cai entre os dois passos, a ocorrência fica `CLAIMED` sem mensagem em fila, e isso NÃO é coberto pela janela de lookback do próprio producer (que consulta `M` outra chave a cada tick) nem necessariamente pela reconciliação diária a tempo. Fila+DLQ sozinhas não fecham essa lacuna (achado que nenhuma das duas propostas independentes tinha isoladamente â€” só apareceu na crítica cruzada).

**Decisão**: o claim grava, na MESMA `TransactWriteItems`, um `OutboxEvent` (reusando `shared/outbox/outbox.ts` — nenhum mecanismo de outbox paralelo), `eventType: "ReminderDispatchRequested"`, com um atributo novo e obrigatório **`destination: "SQS_REMINDER_DISPATCH_V1"`** — o único discriminador de roteamento. `OutboxPublisher` (M2/M3, genérico → EventBridge) só processa itens SEM `destination` ou com `destination` que ele reconhece como "EventBridge padrão"; ao encontrar `destination: "SQS_REMINDER_DISPATCH_V1"` ele **ignora explicitamente** o item (não é "o padrão dele, só que falhando" — é um `if` textual no seu filtro de query/processamento). Só o `DispatchOutboxRelay` Lambda processa itens com esse `destination`. Isso é testado diretamente: um item com `destination: "SQS_REMINDER_DISPATCH_V1"` nunca aparece publicado no EventBridge, e um item sem `destination` nunca é consumido pelo relay SQS.

`DispatchOutboxRelay`: gatilho DynamoDB Streams (`NEW_IMAGE`, filtro no event source mapping por `destination`), `reportBatchItemFailures` (partial batch failure do próprio Stream). Para cada registro: (1) lease condicional — `UpdateItem` com `ConditionExpression: attribute_not_exists(leaseOwner) OR leaseExpiresAt < :now`, evita dois relays concorrentes publicando o mesmo item em paralelo; (2) `SendMessage` para `ReminderDispatchQueue`; (3) `UpdateItem` transição `PENDING→PUBLISHED` só após `SendMessage` confirmado. Falha entre (2) e (3) é aceitável — duplicata é absorvida pela idempotência do dispatch (M3, claim por `occurrenceId` determinístico) — falha antes de (2) deixa o item `PENDING`, recuperável.

**Sweeper** (`OutboxSweeperReminderDispatch`, reusa o mecanismo de sweeper já previsto para `OutboxPublisher` genérico, mesmo padrão): EventBridge Scheduler a cada 5 minutos, varre `GSI6PK=RECON#OUTBOX#PENDING` filtrando `destination: "SQS_REMINDER_DISPATCH_V1"` e `occurredAt` mais antigo que um limiar (2 min — cobre falha do Stream/relay, não falha transitória normal), reenvia via o mesmo caminho do relay (lease condicional inclusive). Retry/backoff: nenhum backoff próprio — cada execução do sweeper é uma tentativa; itens que falham repetidamente continuam `PENDING` e acumulam idade, visível em alarme de "outbox pendente há mais de N execuções do sweeper" (reusa o alarme de outbox já documentado em `implementation-blueprint.md`).

## Reconciliação: precisa de fonte real de candidatos, entra no escopo

`runReconciliation` (M3) recebe candidatos como parâmetro injetado — rodar a Lambda via EventBridge sem uma query real produzindo esses candidatos seria false-green (exatamente o P1 #3 do red team). **Correção de convergência (Rodada 4 de validação)**: a primeira versão desta seção usava `GSI6PK=TENANT#t#WORKSTATE#<status>` (tenant-scoped), mas isso é **inconsultável pelo reconciliador global** — o mesmo erro estrutural já cometido e corrigido no GSI3 (`implementation-blueprint.md` §9.2): `Query` exige `PK` exato, e o job de reconciliação não sabe a priori quais tenants têm claim expirado ou candidato DST. `RECON#OUTBOX#PENDING` (outbox, seção anterior) já resolve isso com uma chave GLOBAL sem tenant — é o padrão a seguir aqui também, não uma exceção nova.

**Decisão**: `GSI6PK` **global** (sem `tenantId`), `tenantId` preservado no `GSI6SK` e no item base para reconstrução de contexto — chave global cria blast radius global deliberado nas funções que a consultam, mesmo trade-off do GSI3, mitigado pela mesma disciplina de IAM explícito (`infra/lib/dynamo-table.ts`, `PolicyStatement`s por recurso, nunca `grantReadData` genérico):

- **Exatamente duas roles** recebem `dynamodb:Query` sobre `<tableArn>/index/GSI6`: `ReminderReconciliation` e `OutboxSweeperReminderDispatch` (o sweeper também precisa consultar `RECON#OUTBOX#PENDING`, que já vive neste índice — não é exclusividade de uma única função, é uma lista fechada de duas, nenhuma tenant-facing).
- Nenhuma outra role (incluindo `ReminderProducer`, `ReminderDispatch`, `RemindersHandler`, `ItemsHandler`) recebe esse grant, mesmo que já tenham `gsi3Read()` ou acesso de tabela — capability nova e distinta em `scoped-lambda-function.ts` (`gsi6Read()`, mesmo padrão de `gsi3Read()`), nunca implícita em `readWriteKeys`/`readKeys`.
- Teste de synth (`test/infra/stack.test.ts`) verifica positivamente que só essas duas roles referenciam `/index/GSI6`, e negativamente que nenhuma outra o faz — mesmo padrão do teste de isolamento do GSI3 (M3).
- Teste de sandbox AWS (Camada 3) exige `AccessDenied` tanto para GSI3 quanto para GSI6 ao assumir a role de uma função tenant-facing.
- Remoção das chaves `GSI6PK`/`GSI6SK` (`WORKSTATE#CLAIMED`/`WORKSTATE#DST_PENDING`) ocorre **atomicamente na mesma `TransactWriteItems`/`UpdateItem` da mudança de estado correspondente** (claim→triggered, claim revertido, janela DST processada) — nunca como passo separado que pode falhar independente e deixar o índice inconsistente com o estado real.

```ts
interface ReminderReconciliationCandidateSource {
  /** GSI6PK="WORKSTATE#CLAIMED" (global), GSI6SK=<claimExpiresAt>#TENANT#<tenantId>#OCCURRENCE#<occurrenceId> — projeção: PK, SK, tenantId, occurrenceId, claimExpiresAt, version. Filtro: claimExpiresAt < now (SK é lexicograficamente ordenável por timestamp primeiro). Paginação: LastEvaluatedKey, página lógica máx. 200. */
  listExpiredClaims(input: { before: string; pageSize?: number; cursor?: string }): Promise<{ items: ExpiredClaimCandidate[]; cursor?: string }>;
  /** GSI6PK="WORKSTATE#DST_PENDING" (global), GSI6SK=<windowStart>#TENANT#<tenantId>#POLICY#<policyId> — projeção: PK, SK, tenantId, policyId, timeZone, windowStart, windowEnd. Filtro: windowStart dentro da janela de 7 dias já usada por M3. Paginação: idêntica. */
  listDstCandidates(input: { window: { start: string; end: string }; pageSize?: number; cursor?: string }): Promise<{ items: DstReconciliationCandidate[]; cursor?: string }>;
}
```

Escrita das chaves (sem isso, ter só a fonte de leitura não torna o índice correto):
- `GSI6PK="WORKSTATE#CLAIMED"`/`GSI6SK` gravados pelo `ReminderProducer` na MESMA `TransactWriteItems` que faz `SCHEDULED→CLAIMED` (builder novo em `occ.ts`, SET, mesmo padrão do GSI3 shard); removidos (ou o builder ganha suporte a REMOVE, gap já documentado em M3 §judgment call 2 — reavaliar aqui, já que agora este ponteiro passa a ser lido ativamente, não só tolerado como órfão) quando o `ReminderDispatch` faz `CLAIMED→TRIGGERED`, e quando a `ReminderReconciliation` reverte `CLAIMED→SCHEDULED` por claim expirado.
- `GSI6PK="WORKSTATE#DST_PENDING"`/`GSI6SK` gravados pelo `ReminderMaterializer` (M3, já existente) ao criar/atualizar uma `ReminderOccurrence` cuja janela de recorrência cruza uma transição de DST conhecida (mesma lógica IANA-aware de M3, só passa a persistir o resultado como candidato indexado em vez de recalcular do zero); removidos quando a reconciliação DST processa a janela.

Namespace `WORKSTATE#CLAIMED`/`WORKSTATE#DST_PENDING` (global, sem tenant) não colide com `RECON#OUTBOX#PENDING` (global, outbox) nem com `TENANT#t#WORKSTATE#<status>` de outros domínios (Document/Upload, M5+, que continuam tenant-scoped por não precisarem de reconciliação cross-tenant) — são famílias de chave `GSI6PK` distintas por prefixo, coexistindo no mesmo índice físico. Port separado de `ReminderStore` (mesmo princípio de isolamento que levou a `ReminderProducerStore` a ser separado — não dar a rotas tenant-facing acesso a uma query que elas não precisam). Isso muda o escopo original: o "wiring real do GSI6" (item 4 da lista de pendências pós-M3) deixa de ser follow-up separado e entra neste milestone — sem ele, a EventBridge Rule/Scheduler de reconciliação (item 4 do escopo de G8) dispara sobre nada.

Cadência: reconciliação de **claims expirados** roda em minutos (curta — recupera leases/claims excepcionais), separada da reconciliação **DST/materialização diária** (mesmo handler, campo `mode` no evento, concurrency reservada 1 preservada); são responsabilidades complementares ao sweeper do outbox (que recupera publicação pendente), não redundantes.

## Componentes do milestone

1. **Adapters DynamoDB reais** (`@aws-sdk/client-dynamodb` + `@aws-sdk/lib-dynamodb`, `DynamoDBDocumentClient`, sem conversões numéricas silenciosas): um por port — `DynamoDbIdentityStore`, `DynamoDbExpirationStore`, `DynamoDbReminderStore`, `DynamoDbReminderProducerStore`, `DynamoDbReminderReconciliationCandidateSource` (contrato completo na seção de reconciliação acima). Nenhuma classe universal implementando todos os ports (evita injeção acidental de acesso a GSI3/GSI6 em código tenant-facing). As escritas condicionais/transacionais (`putIfAbsent`/`update`/`transactWrite`) traduzem 1:1 para os builders já existentes em `shared/dynamodb/occ.ts` — os adapters são tradução fina dessas, não reimplementam OCC/idempotência; os métodos de leitura/query (`get`, `queryByItem`, `queryGsi1`, `queryGsi3`, `listExpiredClaims`, `listDstCandidates`) são `GetCommand`/`QueryCommand` construídos diretamente no adapter (não vêm de `occ.ts`, que só cobre escrita). Erros do SDK mapeados para `shared/errors/app-error.ts` (`ConditionalCheckFailedException`→`false`, `TransactionCanceledException`→`isTransactionCanceled`, throttling/timeout→retryable, validation/`AccessDeniedException`→terminal) só neste adapter — o resto do sistema continua SDK-agnóstico.
2. **Handlers Lambda reais**: bundling via `esbuild` (target `node20`, bundle independente por função, SDK v3 incluído no bundle — não confiar na versão fornecida pela runtime), estendendo `ScopedLambdaFunction` com `entry`/`handlerExport` (único ponto de criação de Lambda continua sendo esse construct). Cada handler é composition root fino (env vars → adapters → lógica de domínio já testada → tradução de protocolo → `SecureLogger`), nenhuma lógica de negócio no wrapper. Handlers obrigatórios deste milestone, com seus gatilhos: `RemindersHandler`/`ItemsHandler`/`TestPingHandler` (API Gateway HTTP), `ReminderProducer` (EventBridge Scheduler), `ReminderDispatch` (SQS `ReminderDispatchQueue`, `reportBatchItemFailures: true`), `ReminderReconciliation` (EventBridge Scheduler, campo `mode`), **`DispatchOutboxRelay`** (DynamoDB Streams, `reportBatchItemFailures: true`), **`OutboxSweeperReminderDispatch`** (EventBridge Scheduler, 5 min). Teste de infra novo: falha se qualquer função continuar com `fromInline`/corpo `501`.
3. **SQS + DLQ**: `ReminderDispatchQueue` Standard (idempotência já é necessária independente de ordenação; FIFO não eliminaria essa necessidade) + DLQ, `maxReceiveCount=5` (já documentado em `implementation-blueprint.md` §26), retenção 4d/14d, visibility timeout ≥6× timeout da Lambda, batch size 10, `reportBatchItemFailures`. Poison message: deixar esgotar `maxReceiveCount` (redrive nativo observável), não deletar/rotear manualmente. O trecho outbox→SQS (`DispatchOutboxRelay`+sweeper) está especificado na seção "Decisão central" acima, não é uma extensão vaga desta fila.
4. **EventBridge Scheduler** (não Rule legado — decisão já fixada em `implementation-blueprint.md` linha 162, Type 1 já aprovada, não reaberta aqui sem necessidade técnica nova): `ReminderProducerSchedule` (**1 min**, `FlexibleTimeWindow: OFF`), `ReminderClaimReconciliationSchedule` (**5 min**, `FlexibleTimeWindow: OFF`), `ReminderDstReconciliationSchedule` (**diário 03:00 UTC, `FlexibleTimeWindow: 15 min`**), `OutboxSweeperReminderDispatchSchedule` (**5 min**, `FlexibleTimeWindow: OFF`). Reserved concurrency preservada do blueprint (producer 2, dispatch 10, reconciliation 1); relay/sweeper concurrency 2 (mesma ordem de grandeza do producer, sem DLQ dedicada para o sweeper — ele mesmo é o mecanismo de recuperação).
5. **Testes em 3 camadas**:
   - Camada 1 (todo PR, rápida): unit/contract/CDK assertions + teste de bundle + proibição de `fromInline` em produção + isolamento estrutural GSI3/GSI6 + **teste de exclusividade de roteamento**: um `OutboxEvent` com `destination: "SQS_REMINDER_DISPATCH_V1"` nunca é publicado pelo `OutboxPublisher` genérico, e nenhum outro `OutboxEvent` é consumido pelo `DispatchOutboxRelay`.
   - Camada 2 (containers): **DynamoDB Local** para a suíte de paridade adapter-real-vs-fake-em-memória (rápida, determinística, é o padrão que M0-M3 já usam); **LocalStack via Testcontainers** só para o que precisa de Streams+SQS+DLQ+EventBridge de verdade — mais pesado, job separado. Toxiproxy para injeção real de timeout/latência de rede (não `mockRejectedValue`).
   - Camada 3 (sandbox AWS efêmero, gate obrigatório — LocalStack não prova IAM real, event source mapping real nem redrive gerenciado real): deploy em conta/região de teste com TTL e cleanup, teste negativo de IAM real (role tenant-facing tentando `Query` em **GSI3 e GSI6** → `AccessDenied` em ambos), poison message até DLQ real, redrive real, invocação manual do schedule. Evidência (CloudWatch request IDs, ARNs, resultados) preservada como prova do gate. Cadência: containers em todo PR; sandbox no merge para `develop` ou workflow manual do milestone.

## Casos obrigatórios de fault injection

OCC concorrente (só um writer vence), claim+outbox atômicos, falha do relay preserva registro para retry (sweeper), duas entregas SQS criam um único `NotificationIntent`, falha de item não repete itens bem-sucedidos do batch, poison message chega à DLQ após 5 receives, claim expirado é recuperado pela reconciliação curta, renew/cancel concorrente faz dispatch cancelar por versão obsoleta, GSI3 encontrado por múltiplos tenants sem misturar contexto, role tenant-facing recebe `AccessDenied` em GSI3/GSI6.

## O que este milestone explicitamente NÃO fecha

Registrar para não ser mal interpretado como "G8 fechado = todos os 5 P1 resolvidos":
- **P1 #1 (pipeline assíncrono sem recuperação)**: este milestone fecha a recuperação do trecho **producer→dispatch** (claim, outbox, relay, sweeper, DLQ, redrive) com evidência real. Não fecha pipelines assíncronos futuros de Notification/Document (M4+), que ainda não existem e terão seus próprios pontos de falha a provar quando forem construídos.
- **P1 #2 (idempotência no limite do efeito externo)**: `NotificationIntent` continua sendo só uma intenção durável — idempotência contra um provedor externo real (e-mail/WhatsApp, timeout depois do provider aceitar e antes de responder) é problema de M4 (Notification), que ainda não existe.
- **P1 #3 (false-green)**: reduzido — adapters, handlers, filas e schedules passam a ser cobertos por teste real — mas não desaparece até M4 rodar sob as mesmas condições e até haver operação continuada real.
- **P1 #4 (concorrência/estado obsoleto)**: provado entre renew/cancel/materialização/dispatch/reconciliation. Não prova corridas envolvendo envio externo/callbacks de M4.
- **P1 #5 (blast radius do GSI3)**: teste IAM real prova que roles tenant-facing não alcançam o índice; o `ReminderProducer` continua sendo componente privilegiado por desenho — blast radius de um bug/comprometimento nele continua global. Alarmes, logs sem PII e revisão dedicada desse handler continuam necessários, fora do escopo mecânico deste milestone.
- Carga extrema, restore real, região/LGPD, provider de notificação, BFF de sessão, aprovação global de `ARCHITECTURE STATUS` (rubrica B) — nenhum desses é tocado aqui.

docs/architecture/data-model.md:45:## 3. GSIs (todos com chave iniciando por `TENANT#tenantId`, exceto GSI3 — ver exceção documentada abaixo)
docs/architecture/data-model.md:48:- **GSI3 — scheduler**: `PK=GSI3PK=DUE#yyyyMMddHHmm#NN`, `SK=GSI3SK=TENANT#t#OCCURRENCE#<occurrenceId>`. 4 shards/minuto inicial (decisão Fase 3 Rodada 4); produtor condiciona por status/versão. **Correção Type 1 (ratificada em `implementation-blueprint.md` §9.2/§9.3, decisions-log.md D-028)**: a chave original acima (`PK=TENANT#t#DUE#...`) não é consultável pelo `ReminderProducer` — `Query` do DynamoDB exige PK exata, e o producer do minuto `M` não sabe a priori quais tenants têm ocorrência em `M`. GSI3 é portanto a **única exceção** à regra "toda chave começa com `TENANT#tenantId`": a PK é global (sem `tenantId`), com `tenantId` preservado na SK e no item base para reconstrução segura do contexto. Salvaguardas obrigatórias (detalhadas em `implementation-blueprint.md` §9.2): IAM do índice restrito exclusivamente ao `ReminderProducer` (nenhuma rota tenant-facing tem `Query` neste GSI); projeção mínima, sem conteúdo de negócio sensível; teste de isolamento automatizado provando que nenhuma API tenant-facing o alcança, direta ou indiretamente; dimensionamento de shards por pico global, não por tenant.
docs/architecture/data-model.md:51:- **GSI6 — retenção/reconciliação**: `PK=TENANT#t#PURGE#yyyyMM` ou `...#WORKSTATE#<status>`, `SK=<purgeAfter/expiresAt>#<type>#<id>`. Suporta purge, upload slots vencidos, inbox/outbox e jobs pendentes num índice único. TTL é limpeza auxiliar, nunca gatilho operacional (evita depender de timing assíncrono do TTL para correção — mesma lição do reconciliador de upload da Fase 3 Rodada 6).

docs/architecture/data-model.md:80:**GSI1 hot partition — correção de erro técnico real**: a mitigação original ("aplicar shard ao `GSI1SK`") estava errada — a partição física do DynamoDB é determinada pela **PK**, não pela SK; adicionar shard à SK não distribui carga nenhuma. Corrigido: se o volume por tenant/status justificar (critério quantitativo a extrair do capacity model, não decidido a priori), o shard entra na **PK**: `GSI1PK=TENANT#t#ITEMSTATUS#<status>#SHARD#<NN>`, exigindo fan-out de leitura (consultar todos os shards e mesclar) no lado da aplicação. **Para o MVP, não shardar é a decisão correta** — volume por tenant é baixo (`capacity-model.md`, Stage 0–2) e a complexidade de fan-out não se justifica ainda; gatilho de ativação: mesmo padrão de alarme de `ConsumedReadCapacity` já usado no GSI3 (scheduler, decisão Fase 3 Rodada 4).

# Proposta independente de pesos

Base normativa preservada:

- Arquitetura: ISO/IEC 25010, AWS Well-Architected e ATAM.
- Qualidade de Engenharia: ISO/IEC 25010 Maintainability e DORA/Core-4.
- Engenharia de Contexto: mesmas fontes de context engineering, ADR lifecycle, Diátaxis e progressive disclosure do documento-fonte.

Todos os critérios foram mantidos, sem adições ou remoções. Os pesos somam exatamente 100% em cada eixo.

## 1. Arquitetura

| # | Critério | Fonte | Proposto | Δ |
|---:|---|---:|---:|---:|
| 1 | Domain Fit & Simplicity | 11% | **8%** | -3 |
| 2 | Reliability & Fault Recovery | 13% | **17%** | +4 |
| 3 | Event & Integration Correctness | 10% | **10%** | 0 |
| 4 | Data Model & Consistency | 10% | **15%** | +5 |
| 5 | Security & Privacy | 11% | **14%** | +3 |
| 6 | Modifiability & Evolvability | 9% | **7%** | -2 |
| 7 | Observability & Operability | 9% | **7%** | -2 |
| 8 | Testability & Delivery Safety | 8% | **8%** | 0 |
| 9 | Cost & Resource Governance | 6% | **4%** | -2 |
| 10 | Performance & Scalability Fitness | 5% | **3%** | -2 |
| 11 | Architecture Governance & Traceability | 8% | **7%** | -1 |
|  | **Total** | **100%** | **100%** | |

Justificativas dos movimentos superiores a 2 p.p.:

- **Domain Fit & Simplicity, 11% → 8%:** o domínio funcional é relativamente estreito e já está bem delimitado. Os maiores riscos atuais não estão em descobrir o domínio, mas em preservar correção distribuída e isolamento.
- **Reliability & Fault Recovery, 13% → 17%:** G8 é o gate mais caro e ainda não está tecnicamente fechado sem a Camada 3. O protocolo de M3.5 encontrou defeitos reais em outbox, redrive, paginação, limpeza de índice e uma race condition. Recuperação assíncrona é o risco arquitetural dominante.
- **Data Model & Consistency, 10% → 15%:** a single-table com seis GSIs, OCC, transações multi-item e chaves globais GSI3/GSI6 concentra decisões Type 1 difíceis de migrar. Erros anteriores de consultabilidade de PK e limpeza de ponteiros demonstram risco concreto, não hipotético.
- **Security & Privacy, 11% → 14%:** GSI3/GSI6 criam blast radius cross-tenant deliberado e dependem de IAM negativo real ainda não provado em sandbox. A região de produção e suas consequências para LGPD também permanecem abertas.

Leitura geral: este eixo deve penalizar fortemente uma arquitetura que pareça elegante, mas não demonstre recuperação, consistência transacional ou isolamento dos índices globais.

Justificativas dos movimentos superiores a 2 p.p.:

- **Test Effectiveness & Coverage Discipline, 14% → 17%:** o histórico comprova que testes orientados a risco encontram problemas relevantes. DynamoDB Local já acrescentou evidência além das fakes, mas IAM, Scheduler e redrive gerenciados ainda exigem teste AWS real.
- **Delivery, Release & Recovery Discipline, 8% → 14%:** este é o maior ajuste do eixo. Não existe deploy real validado, e o único bloqueador atual de G8 é justamente executar deploy, IAM negativo, DLQ/redrive e Scheduler numa sandbox AWS. Para este estágio, qualidade de entrega não pode ser um critério secundário.
- **Documentation–Implementation Drift Control, 7% → 4%:** continua relevante, mas o repositório já possui precedência explícita, correções históricas documentadas e disciplina de handoff. O risco incremental é menor que o de runtime real.
- **Technical-Debt & Continuous-Improvement Practice, 6% → 3%:** há registro explícito de exceções, prazo de revisão, decisões e gatilhos. Deve continuar avaliado, mas com menor poder de compensar falhas em testes e recuperação operacional.

Aqui, uma suíte extensa baseada apenas em fakes não deve obter nota alta: a efetividade precisa ser julgada pela capacidade de provar propriedades reais de DynamoDB, IAM, SQS/DLQ e EventBridge.
