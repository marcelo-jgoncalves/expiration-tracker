## Achados desta rodada

### 1. Inventário desatualizado — D-231 não refletido (BLOQUEANTE, critério 2)
`docs/engineering/third-party-inventory.md` linha "BSP WhatsApp (não escolhido)" está **stale**: D-231 (2026-09-08, `docs/architecture/decisions-log.md`) já implementou o adapter real contra a **Meta Cloud API** (Graph API, `whatsapp-cloud-api-adapter.ts`), com **secret real em AWS Secrets Manager** (`secrets-manager-whatsapp-config.ts` — accessToken/appSecret/phoneNumberId/wabaId/verifyToken) e rota pública de webhook (`whatsapp-webhook-handler.ts`). O próprio prompt desta auditoria chama D-231 de "PRIMEIRO secret de vendor externo real do repo" — e o inventário, que existe exatamente para capturar isso, ainda mostra o fornecedor como "não escolhido". A seção "Como manter atualizado" do próprio arquivo diz explicitamente que uma linha deve ser adicionada "antes de habilitar o fluxo em produção" — regra própria não seguida quando o vendor real entrou em `dev`. Ainda que `dev` não seja produção, o secret e o código já existem e processam webhooks reais da Meta; a lacuna documental é real, não é só formalismo — devida diligência (certificação Meta, DPA, região de processamento) não pode nem começar enquanto o inventário não nomeia o fornecedor real.

**Fix mecânico (nível 1-2) aplicado nesta sessão**: substitui a linha "BSP WhatsApp (não escolhido)" por uma linha real "Meta Platforms, Inc. (WhatsApp Business Cloud API)" com colunas preenchidas onde há evidência de código (serviço, dados tratados, criticidade, lock-in) e "pendente"/"não decidida" honesto onde não há (região de processamento da Meta, certificação, DPA assinado, responsável nomeado) — ver seção "Fix aplicado" abaixo.

### 2. Licenciamento OSS — sem achado bloqueante, uma observação de proveniência (critério 3)
`npm ls --prod --depth=0` (20 pacotes diretos) + `npx license-checker --production --summary` (143 pacotes na árvore completa de produção): MIT 74, Apache-2.0 49, ISC 13, BSD-3-Clause 3, MIT* 2, 0BSD 2, Unlicense 1, UNLICENSED 1 (o próprio projeto), `(MIT AND Zlib)` 1, **`(MIT OR GPL-3.0-or-later)` 1**, **`Custom: http://github.com/substack/node-bufferlist` 1**.

- **`jszip@3.10.1`** (transitivo via `exceljs`) é dual-licenciado MIT/GPL-3.0-or-later — biblioteca deliberadamente oferece as duas opções para o consumidor escolher; **operar sob os termos MIT é uma escolha legítima e comum**, não gera obrigação de copyleft por si só, mas essa escolha nunca foi registrada em lugar nenhum do repositório (nem `third-party-inventory.md`, nem um `NOTICE`/`THIRD-PARTY-LICENSES` file). Isso é o gap real: não é risco de licença GPL bloqueante (a alternativa MIT existe e é a que se aplica por eleição do licenciado), é ausência de **evidência escrita da eleição** — se auditado externamente, a falta de um registro explícito "operamos jszip sob MIT, não GPL" é uma lacuna de due diligence, não uma violação.
- **`buffers@0.1.1`** (transitivo, também via `exceljs`) declara licença "Custom" apontando para uma URL do GitHub (`github.com/substack/node-bufferlist`) que não é o pacote em si — texto de licença não verificável programaticamente nesta sessão (`WebSearch` não disponível para esta subtarefa dentro do orçamento). Risco baixo (pacote de baixo nível, sem API exposta a usuário final), mas não confirmado.
- Nenhuma dependência de produção direta ou transitiva com AGPL/SSPL/copyleft forte não-mitigável foi encontrada.
- **Nenhum destes achados foi corrigido nesta sessão** (não é mecânico nível 1-2 — decidir a postura formal do projeto sobre dual-licenciamento é decisão de governança, registrada como achado, não point-fix).

### 3. Termos da Meta Cloud API vs. comportamento do código — D-4 confirmado, LGPD/DPA não (critério 1, 5, 6)
Verificado por leitura direta do código (não apenas da decisão registrada): `whatsapp-cloud-api-adapter.ts` linha ~104-108 comenta explicitamente `// D-4: every message is category Utility (never Marketing) - enforced by only ever sending pre-provisioned Utility templates` — **confirmado como respeitado**: o adapter nunca envia `type: "text"` livre para o canal WhatsApp, só `type: "template"` com templates pré-provisionados fora de banda (D-3), o que é exatamente o mecanismo que a Meta exige para mensagens fora da janela de 24h de atendimento ao cliente (mensagens de utilidade/notificação, categoria `UTILITY`, não `MARKETING`) — a Meta rejeitaria/penalizaria uma tentativa de enviar texto livre fora da janela de 24h de qualquer forma, então o design também é tecnicamente forçado, não só uma boa prática documentada.

Nenhum artefato do repositório (nem `third-party-inventory.md`, nem `privacy-lgpd.md`) documenta: (a) que a Meta processa o conteúdo da mensagem e o número de telefone do titular como subprocessadora real desde D-231; (b) se a Meta oferece DPA padrão para WhatsApp Business Platform (a Meta de fato oferece um "Data Processing Terms" para clientes de API comercial, mas confirmar isso é pesquisa externa — ver pedido ao Codex abaixo) e se esse DPA foi de fato revisado/aceito; (c) a região de processamento de dados da Meta (WhatsApp Business Platform historicamente processa fora do Brasil). Isso é o mesmo padrão de gap já identificado no round1 para AWS (DPA "padrão", não verificado formalmente) — agora replicado para um segundo fornecedor real, sem que o inventário sequer o cite ainda (achado 1).
