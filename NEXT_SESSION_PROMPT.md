Escopo: (1) `GET /import-jobs/{jobId}/schema` (§3 — `Range` GET dos primeiros 64 KiB do S3, `sniffCsvHeaderAndSample()`, `objectETag` não-autoritativo); (2) `POST /import-jobs/{jobId}/mapping` (§3 — grava `columnMapping`/`columnMappingSha256` sob OCC, mesma `TransactWriteItems` emite o outbox `SQS_IMPORT_PARSE_V1` novo quando o resultado calculado é `PARSING`); (3) Terraform: fila SQS+DLQ dedicada para `SQS_IMPORT_PARSE_V1` (mesmo padrão de `SQS_REMINDER_DISPATCH_V1`), IAM restrito, `OutboxDestination` ganha o literal novo; (4) `proxy-allowlist.ts`: as duas rotas HTTP novas precisam entrar na allowlist do BFF, senão retornam 404 mesmo com o handler implementado (achado recorrente de fatias HTTP anteriores neste projeto — sempre checar isso antes de declarar uma rota pronta). §8 (limite de 200 bytes/rejeição de `#` em `externalId`) e o dedupe fraco por `displayName`/`nameNormalized` continuam registrados como pré-requisitos pendentes de fatias anteriores, não resolvidos por esta lista — só entram se a fatia 9 tiver orçamento sobrando depois do essencial acima.

**Fatia 6 Parte B — DEFERIDA para fatia 7 (decisão explícita desta sessão, não um corte silencioso)**: conectar `resolveSubjectReferences()` (fatia 5) + `resolveDocumentTypeReferences()` (fatia 6A) ao loop de `parseImportJob()` para jobs `targetEntityType="Document"|"Requirement"` revelou-se maior do que "wiring" puro na leitura direta do código — `import-row.ts`/o loop de parse hoje são inteiramente TrackedSubject-shaped: `RawImportRow`/`ValidatedImportRow`/`ImportRowPlanEntry` só têm os campos fixos `displayName`/`type`/`externalId`/`notes`/`tags`, e nada no loop lê `job.columnMapping` para extrair coluna por nome (`ColumnMapping.columns.subjectRef` etc.) — abrir isso exige, no mínimo: (1) `RawImportRow`/`ValidatedImportRow`/`ImportRowPlanEntry` ganharem variantes discriminadas por `targetKind` (Document/Requirement têm formas de linha bem diferentes de TrackedSubject — `subjectRef`+`documentTypeRef`+`hasValidity` vs. `subjectRef`+`name`+`notes`+`applicability`); (2) uma função de extração de campo por `ColumnMapping` (hoje `mapCsvRowsToNamedFields` já produz um dict por header, então o `FIELD_CATALOG` do design §2 precisa decidir QUAIS chaves desse dict ler por `targetKind`); (3) dedupe específico por tipo (§7 da régua: `Requirement` usa `RequirementNamePointer`/`subjectId+nameNormalized`, `Document` só quando `externalId` presente, nenhum fallback fraco) — nenhum dos dois está implementado ainda; (4) coletar os `Set`s de referência DISTINTAS ANTES do loop linha-a-linha (a exigência batched das fatias 5/6A só funciona se o chamador junta os valores crus do arquivo inteiro primeiro, não resolve por linha). Isso é substancialmente mais que "chamar os dois resolvers dentro do for" — é a extensão real do domínio de linha de import para 3 formas por `targetKind`. Fatia 7 (nome exato): estender `import-row.ts` com as variantes de `RawImportRow`/`ValidatedImportRow`/`ImportRowPlanEntry` para Document/Requirement + a extração por `ColumnMapping` + o dedupe por tipo do §7, DEPOIS ramificar `import-parse-service.ts` em `targetEntityType` para coletar os `Set`s de referência distintas do batch inteiro, chamar `resolveSubjectReferences()`/`resolveDocumentTypeReferences()` uma vez cada, e produzir entradas de plano com `subjectId`/`documentTypeId` já CONGELADOS — ainda SEM chamar `buildCreateDocumentEntries`/`buildCreateRequirementEntries` nem tocar o commit worker (essa é a fatia 8, que por sua vez precisa do `ImportRowOutcome`/fallback de linha do design §6, não decidido ainda) nem a orquestração HTTP `GET /schema`/`POST /mapping` (§3, consome o `AWAITING_MAPPING` da fatia 4 pela outra ponta — fatia própria, número ainda não atribuído).

**Próxima fatia real, não iniciada**: extensão da state machine do `ImportJob` — estado `AWAITING_MAPPING` entre `UPLOADED` e `PARSING` com claim OCC atômico, tipo `ColumnMapping` (união discriminada por `targetKind`, §2 do design) substituindo o `mappingVersion: number` morto, `ImportTargetEntityType` ganhando `"Document" | "Requirement"` (hoje só `"TrackedSubject"`) — seguir o design consolidado linha a linha (§2/§3), não reabrir o protocolo salvo achado real durante a implementação. A fiação dos dois planejadores (`buildCreateDocumentEntries`/`buildCreateRequirementEntries`, ambos prontos) no commit worker de import, a resolução de referência batched externalId→subjectId (§4), o dispatch outbox/SQS, e os novos handlers HTTP (`/schema`, `/mapping`) continuam todos sem começar — fatias futuras separadas.
